## Диагностика

### Симптом и что оказалось на самом деле
Заказчик: «постоянно при постинге исчезает обложка».

Проверка прод-БД: **0 новостей без обложки** (136 из 136 имеют `cover_image_id`). Значит запись `NULL` не происходит — фикс `removeCover` (Gotcha #5, май 2026) на сервере присутствует и работает.

Ломалось отображение.

### Корневая причина
Next.js в standalone-режиме строит индекс папки `public/` **один раз при старте процесса**. Файл, загруженный через `/api/files` уже после старта PM2, этому индексу неизвестен.

Внутренний fetch image-оптимизатора идёт сам на себя (`127.0.0.1:3004`), **минуя nginx**, и упирается в 404 → оптимизатор отдаёт 400 вместо картинки.

Воспроизведено вживую (файл положен на диск после старта процесса):

| Файл | static `:3004` | `/_next/image` | через nginx |
|---|---|---|---|
| залит ДО старта PM2 | 200 | 200 | 200 |
| залит ПОСЛЕ старта PM2 | **404** | **400** | 200 |

### Почему выглядело именно как «исчезает при постинге»
- В админке превью рендерится обычным `<img>` (`ImageCropUploader.tsx:199`) — обложка **видна**, всё выглядит нормально.
- Публичный сайт использует `<Image>` из `next/image` — там **пусто**.

### Почему баг казался «плавающим»
`ecosystem.config.js` → `cron_restart: "0 4 * * *"`. Каждую ночь процесс перезапускается, индекс `public/` перестраивается, и все накопленные за сутки картинки «чинятся сами». Отсюда паттерн «сегодня обложки нет, а завтра появилась».

Сессия заказчика ровно об этом: файлы 222–226 залиты в 02:52–03:12, процесс работал со вчерашнего утра → все пять обложек на сайте не отображались.

## Что сделано

### 1. `src/app/api/uploads/[...path]/route.ts` (новый)
Route handler читает файл из `public/uploads/<folder>/<filename>` **в момент запроса** через `readFile` — то есть индекс, построенный при старте процесса, больше не при чём.

Ограничения доступа:
- whitelist папок: `media`, `documents`, `knowledge`;
- whitelist расширений (изображения + pdf/doc/docx/xls/xlsx);
- отказ при `..`, `/`, `\` в имени файла;
- ровно 2 сегмента пути (`saveToDisk` в `/api/files` всегда пишет как `<folder>/<filename>`).

Путь строится как `process.env.APP_DIR || process.cwd()` — так же, как в `saveToDisk`. **Важно:** в standalone `process.cwd()` = `.next/standalone`, поэтому `APP_DIR` в `.env.local` обязателен (там он задан: `APP_DIR=/var/www/gbu-anic`).

`.svg` намеренно **не** включён в whitelist: в `uploads/` их нет, а отдача `image/svg+xml` со своего домена — вектор XSS.

### 2. `next.config.ts` — rewrite
```ts
async rewrites() {
  return {
    beforeFiles: [{ source: "/uploads/:path*", destination: "/api/uploads/:path*" }],
    afterFiles: [],
    fallback: [],
  };
}
```

`beforeFiles` критично — перехват должен произойти **до** проверки файловой системы, иначе static handler успеет вернуть 404.

Компоненты (10 файлов с `next/image`) и `url` в таблице `files` не трогали вообще.

## Тупиковый вариант (важно не повторить)

Первым подходом был кастомный `images.loader: "custom"` + `loaderFile`, переписывающий src на `/api/uploads/`.

**Не работает и ломает прод:** при `loader: "custom"` встроенный эндпоинт `/_next/image` в Next 16.1.6 перестаёт существовать — отдаёт 404 (HTML 404-страницу приложения) **для всех** картинок, включая статику из репозитория (`/logo-anic.png`). Проверено эмпирически на проде.

Между двумя сборками (~3 минуты) картинки на сайте были битыми. Откачено, переделано через `rewrites`.

Custom loader пригоден только когда оптимизацией занимается внешний CDN.
